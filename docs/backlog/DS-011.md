# DS-011 [Class Normalizer] Normalizar clases CSS y extraer tokens semánticos

Fuente: https://github.com/Kilexmommm/DesAIgnSync/issues/11

---

## Objetivo
Usar nombres de clases como señal útil sin convertirlos en fuente autoritativa de identidad de componente.

## Historia de usuario
Como motor de matching, quiero extraer significado de clases como `btn-primary`, `form-control` o `card-header`, pero ignorar hashes y nombres generados para reducir falsos positivos.

## Prioridad
P0

## Reglas
- Conservar siempre `rawClasses`.
- Generar `normalizedClassTokens` por separado.
- Tokenizar kebab-case, snake_case, camelCase y prefijos comunes.
- Detectar/penalizar clases probablemente generadas por CSS Modules, hashes o bundlers.
- Permitir diccionario configurable de tokens relevantes: `btn`, `button`, `primary`, `form`, `control`, `input`, `select`, `card`, `header`, etc.
- No inferir cumplimiento o componente exclusivamente por clase.

## Ejemplos esperados
- `button.btn-primary` → semántica fuerte de button + tokens `btn`, `primary`.
- `div.btn-primary` → tag div; clase solo aporta señal secundaria.
- `div[role=button].primary-action` → candidato funcional a button, conservando alerta semántica por tag no nativo.
- `input.form-control[type=email]` → input/email primero; `form-control` como señal secundaria.
- `_button_x7f31_2` → tokens generados con baja confianza semántica.

## Criterios de aceptación
- [ ] Existe función pura y testeable de normalización.
- [ ] Raw class list nunca se pierde.
- [ ] Se detectan patrones hash/configurables sin borrar clases arbitrariamente.
- [ ] Cada token puede indicar `semanticWeight`/calidad de señal.
- [ ] Los ejemplos definidos tienen tests unitarios.
- [ ] El matching puede funcionar aunque no haya clases útiles.
- [ ] La clase nunca eleva por sí sola un candidato a certeza alta.
