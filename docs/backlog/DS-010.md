# DS-010 [Evidence] Definir modelo de evidencia DOM/ARIA/CSS/geometry/screenshot

Fuente: https://github.com/Kilexmommm/DesAIgnSync/issues/10

---

## Objetivo
Crear un esquema único de evidencia que represente lo observado en la página antes de cualquier interpretación del LLM.

## Historia de usuario
Como motor de validación, quiero trabajar sobre evidencia estructurada y auditable para separar hechos observados de inferencias del modelo.

## Prioridad
P0

## Campos mínimos por elemento
- selector/locator interno no persistente;
- tag HTML;
- role explícito e implícito;
- ARIA relevantes;
- type para inputs/buttons;
- atributos útiles (`name`, `placeholder`, `href`, `disabled`, etc.);
- texto/accessible name/label;
- jerarquía padre-hijo inmediata y contexto cercano;
- raw class list;
- normalized class tokens;
- computed styles seleccionados;
- geometry/bounding box;
- estados observables;
- screenshot/crop opcional;
- URL y timestamp;
- fuente de cada dato: Chrome MCP/tool.

## Principio de inferencia
El tipo funcional debe inferirse priorizando:
1. semántica nativa del tag;
2. role/ARIA;
3. atributos/tipo;
4. estructura y label/contexto;
5. clases CSS;
6. computed styles;
7. evidencia visual.

## Criterios de aceptación
- [ ] Existe un tipo TypeScript versionado para `ElementEvidence`.
- [ ] Distingue `observed`, `derived` y `unknown`.
- [ ] No mezcla findings con evidencia bruta.
- [ ] Puede serializarse para tests sin incluir secretos.
- [ ] Un `input[type=email].form-control` se representa como input de email antes de interpretar la clase.
- [ ] Un `div[role=button]` conserva tag `div` y role `button`; no se transforma en `<button>`.
- [ ] Screenshot es opcional y tiene metadata de origen.

## Dependencias

## Nota
El LLM debe recibir este modelo ya normalizado, no HTML completo indiscriminadamente.
