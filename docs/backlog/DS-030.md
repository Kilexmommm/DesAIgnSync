# DS-030 [Docs & Release] Documentar arquitectura, configuración y criterio de release inicial

Fuente: https://github.com/Kilexmommm/DesAIgnSync/issues/30

---

## Objetivo
Cerrar la primera versión construible con documentación técnica y operativa suficiente para que otro desarrollador o coding agent pueda mantenerla y desplegarla.

## Historia de usuario
Como equipo de desarrollo, quiero documentación actualizada y un criterio claro de readiness para saber cuándo DesAIgnSync puede considerarse utilizable de extremo a extremo.

## Prioridad
P1

## Documentación requerida
- arquitectura MCP-first;
- diagrama Extension → Local Host → MCP/LLM;
- configuración de Chrome DevTools MCP;
- configuración Design System MCP y preset Storybook MCP;
- configuración OpenAI-compatible;
- almacenamiento de secretos;
- esquema ElementEvidence;
- esquema ComponentSignature;
- algoritmo de matching y pesos default;
- Rules Engine y tolerancias;
- Core System Prompt vs Advanced Validation Prompt;
- perfiles Simple/Advanced/Expert;
- privacidad y prompt injection;
- troubleshooting;
- guía de desarrollo local;
- guía de release.

## Definition of Done de la primera release
- DS-001 a DS-018 críticos terminados.
- DS-020, DS-022, DS-024 y DS-028 terminados.
- Chrome DevTools MCP probado en una página real.
- Design System MCP probado con al menos Button/Input/Card.
- OpenAI-compatible probado con modelo manual y provider sin `/models`.
- revisión de elemento genera checklist reproducible.
- no hay secretos en extensión/logs/exports.
- suite crítica verde.

## Criterios de aceptación
- [ ] README permite arrancar proyecto desde cero.
- [ ] Docs contienen ejemplos de configuración sin secretos reales.
- [ ] Las decisiones arquitectónicas clave quedan registradas.
- [ ] Cada schema público tiene ejemplo JSON.
- [ ] Existe checklist de release reproducible.
- [ ] La documentación referencia las historias DS relacionadas.
- [ ] Se documentan limitaciones conocidas: iframe cross-origin, closed shadow root, canvas y evidencia dinámica.
